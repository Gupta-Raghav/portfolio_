02 / the runtime

One ghost. Every client.

Kiro runs in its own IDE, the terminal, the browser, inside Crew, and in any editor that speaks the Agent Client Protocol. Each of them is a client of the same agent runtime. The rule in that layer: a feature cannot assume which client is on the other side, so revert, persistence and context behave the same everywhere, and a fix ships to all of them at once.

03 / deep dive: large tool output

Same ten tool calls. Different context window.

problem

Big outputs did three kinds of damage. They filled the window, they forced early and expensive summarization, and they disturbed the prompt cache so every following turn cost more.

approach

Catch oversized results before they reach the model, move them aside, and leave a short preview with a pointer the agent can follow. Only outputs that can grow without bound qualify; reads that are already bounded stay as they are.

tradeoff

The model sees less by default. The preview usually shows the error and the summary line, which is enough to pick the next step. When it is not, the agent searches the saved output, and the session keeps everything so replay loses nothing.

impact

A huge tool response now costs a sliver of the context it used to. Summarization comes later and stays on the cheap path, and the design became one of the building blocks of how Kiro manages context. I shipped it as an experiment, proved it out, then turned it on for everyone.

checkpoints

Undo for an agent that edits many files

A bad multi-file edit five turns ago had no clean undo, sub-agents edited files the parent never saw, and any client could ask for the revert. I drove the experience with UX and Product, took the design through review, and shipped it. Every edit is now reversible from any message, in any client.

summarization

Sessions that outlive the context window

At the limit, the conversation was simply lost, and the old compaction broke the prompt cache. I designed it around the prompt cache: a primary path that reuses what the model already has cached, and a fallback that always succeeds when the window is nearly full. Then I brought it into the unified runtime so every client gets it. Sessions carry on by themselves, at about the cost of one turn.

memory

Memory that refuses secrets

Cross-session memory is useful until someone pastes an API key and it gets remembered. Every memory write is scanned for credential-shaped strings before it reaches disk. Preferences follow you between sessions. Keys do not.
