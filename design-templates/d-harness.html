02 / deep dive

Large tool output, handled.

One npm test can print 200,000 characters. Dropped straight into the conversation, that single response crowds out everything the agent actually needs to remember.

Ten tool calls, 40k characters each

Problem

Big outputs did three kinds of damage. They filled the window, they pushed usage past the point where the cheap summarization path works, and every insert shifted token positions so the prompt cache stopped hitting.

Approach

Intercept tool results before they enter the model's context. Above a size threshold, write the full text to disk and replace it with a head and tail preview. Only tools with unbounded text output qualify: shell, process logs, web fetch, search, and MCP tools. read_file stays out because it is already bounded and can be re-read by path.

Tradeoff

The model sees less by default. In practice the head shows the error and the tail shows the summary line, which is enough to decide the next step. When it is not, the file is one grep away. The saved session keeps the full output, so replay loses nothing.

Result

Each large response costs about 1k characters of context instead of tens of thousands. Summarization comes later and lands on the cache-friendly path. It shipped behind an experiment flag, and once the numbers held, I made it the default and removed the flag.

More from the runtime

Same format each time: what broke, what I changed, and what it does now.

Checkpoints and revert

agent runtime
problemA bad multi-file edit five turns ago had no clean undo, sub-agents edited files the parent never saw, and any of four clients could ask for the revert.
approachSnapshot every file before a write, deduplicated by content hash. Revert restores each file to its first pre-change state, sub-agent edits included.
impactRevert from any message in any client, including renames across files and files the agent created or deleted. Undo is a new log entry, never an edit. I owned it from UX through design review to rollout.

Summarization

context
problemAt the context limit, the conversation was simply lost. The earlier compaction approach also broke the prompt cache, so it was slow and expensive.
approachTwo paths. Between 80% and 95% usage, re-send the cached prefix with a summary prompt appended, so compaction rides the cache. Above 95%, a truncation path that always succeeds. Then I ported it into the unified runtime.
impactSessions keep going on their own. Compaction costs about as much as one turn, and manual /compact runs the same path.

Memory with a secret scan

memory
problemCross-session memory is useful until someone pastes an API key and it gets remembered.
approachScan every memory write for credential-shaped strings before it touches disk, and refuse with a clear message.
impactPreferences follow you between sessions. Keys do not.

Kiro everywhere

platform
problemKiro was heading to a Mac-first launch. File edits and shell commands assumed Unix paths and one shell, and nobody had bandwidth for the gap.
approachI set up Windows and Linux machines, root-caused the path normalization failures, fixed line endings and URI encoding, added shell detection, and got Linux smoke tests running.
impactKiro launched with Windows and Linux support, and the same agent behavior on all three.

Reasoning effort

models
problemNew models expose how hard they think, and each provider describes it differently.
approachI owned the design across the agent and the IDE, and argued with Science and Product that effort and thinking are separate controls, not one slider.
impactPick a model, then set its effort, with the same control on every client.
