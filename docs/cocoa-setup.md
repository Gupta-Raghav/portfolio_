# Cocoa: Google sign-in and isolated workspaces

Cocoa now uses Google OpenID Connect through Auth.js. The frontend is a public, generic sign-in shell, not a client-side security boundary. All user data is fetched and written by authenticated, server-authorized endpoints. Missing configuration denies access; there is no anonymous, localStorage, or development-auth fallback.

## Isolation guarantees and limits

- The server accepts exactly two configured, verified Gmail identities. Milk maps to Ananya; Mocha maps to Raghav. Identity comes from Google's verified OIDC claims, never a requested profile, email, user ID, or a browser dropdown.
- Use **two distinct private Vercel Blob stores**, with separate server-only credentials. Each account's token is selected server-side. Each document path also includes a SHA-256 digest of the immutable Google subject. Neither person receives a storage credential or a direct Blob URL.
- Every workspace read/write independently checks the encrypted Auth.js session, the current email allowlist, and the tab's expected account identity. An old tab cannot write one person's data into the other person's newly authenticated session.
- No private workspaces, drafts, or OAuth tokens are stored in localStorage/sessionStorage. Workspace state is in tab memory and private server storage. Logout removes the UI and broadcasts logout to other tabs. Returning tabs revalidate identity before showing content.
- Updates use ETags and conditional writes, so a stale tab/device cannot silently overwrite newer data. Failed saves remain in memory, with an unsaved warning and export available. Closing an unsaved tab can lose that pending change.
- This separates the two **application accounts and data stores**, not Vercel project administrators. Someone controlling the project's source, environment variables, or Vercel account can access the backend. Do not give both people infrastructure-admin access if they must not administer each other's data. Separate agent runtimes/VMs and connector credentials are a future requirement; no agents run here yet.
- The older public prototype stored both demo workspaces under `morrow.prototype.v1`. Cocoa never reads or imports this shared browser record. It is not silently deleted, because that would destroy prior user-created data. If it contains private information, its owner must export/remove it from the original browser before sharing that browser; it predates authenticated isolation.

## Required setup in the portfolio Vercel project

Do not put these values into source code, `REACT_APP_*`, client bundles, or chat. Add them in **Vercel Project → Settings → Environment Variables** for the intended production project only:

| Variable | Value |
| --- | --- |
| `AUTH_URL` | `https://portfolio-nine-woad-49.vercel.app` |
| `AUTH_GOOGLE_ID` | Google Web application OAuth client ID |
| `AUTH_GOOGLE_SECRET` | Google OAuth client secret |
| `AUTH_SECRET` | A new Auth.js session-encryption secret, at least 32 characters; generate with the official Auth.js CLI or a cryptographic secret manager |
| `COCOA_RAGHAV_EMAIL` | Raghav's approved Google email, supplied privately by the owner |
| `COCOA_ANANYA_EMAIL` | Ananya's approved Google email, supplied privately by the owner |
| `COCOA_RAGHAV_READ_WRITE_TOKEN` | Generated by connecting Raghav's **private** Blob store with prefix `COCOA_RAGHAV` |
| `COCOA_ANANYA_READ_WRITE_TOKEN` | Generated by connecting Ananya's separate **private** Blob store with prefix `COCOA_ANANYA` |

The supplied email values are recorded only in the Git-ignored `.env.local` in the development workspace. The addresses are not published in the repository or sent to the browser. Do not use the same Blob store for both variables even if it has multiple tokens. Create the stores empty and private, verify anonymous denial for a harmless test object before uploading any private content, and keep them private. The SDK explicitly requests `access: 'private'` on all storage operations. Store provisioning may incur Vercel storage charges and requires the owner's approval.

## Google Auth Platform setup

1. In [Google Cloud Console](https://console.cloud.google.com/auth/overview), choose/create the owner's personal project. Configure the consent screen as **External**, with Cocoa as the application name and the owner's support contact. Do not use an employer-owned project for this personal app.
2. In testing mode, add only the two supplied Google addresses as test users. The application also checks its own exact allowlist, so changing Google's test-user list does not bypass Cocoa's authorization.
3. Create an OAuth client with application type **Web application**. Authorized JavaScript origin: `https://portfolio-nine-woad-49.vercel.app`.
4. Add this exact authorized redirect URI:
   `https://portfolio-nine-woad-49.vercel.app/api/auth/callback/google`
5. Configure the client ID and secret privately in Vercel. The requested scopes are only `openid email profile`. Signing in does not grant Gmail, Calendar, Drive, or other connector permissions.
6. Publish/redeploy only after the configuration has been reviewed. Setting a Google client ID alone does not activate the flow. Without all auth settings, `/api/cocoa/session` returns 503 and the Google button is disabled. Without both storage tokens, authenticated users cannot open any workspace.

Google [provider reference](https://authjs.dev/reference/core/providers/google), Auth.js [core reference](https://authjs.dev/reference/core), and Vercel [private Blob SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk) are the implementation references. Auth.js supplies OIDC signature/issuer/audience validation, PKCE, state, nonce, CSRF protection, encrypted session cookies, Secure/HttpOnly/SameSite flags, and sign-out. No custom authentication protocol is implemented.

## Local validation

Use Node 24.x as specified by the portfolio package. From the repository root:

```sh
npm ci
node --env-file-if-exists=.env.local tools/companion/serve.cjs
```

This listener stays on `127.0.0.1:4173`. Local OAuth additionally needs `http://127.0.0.1:4173/api/auth/callback/google` registered in Google. Never disable checks or use a wildcard listener to make development work.

```sh
node --test tools/companion/state.test.mjs tools/companion/auth.test.mjs
npm --prefix tools/companion ci
npm --prefix tools/companion run test:browser
npm run build
```

Browser tests mock the API **in the test browser only**, never through a server bypass. Backend tests use encrypted Auth.js test sessions and an in-memory storage double to exercise owner isolation, anonymous/forged/expired denial, invalid origins, attempted owner injection, stale-tab identity changes, and conflicting revisions. These tests do not substitute for the production acceptance checks below.

## Production acceptance gate

Before declaring authentication ready, verify:

- The portfolio root remains publicly accessible, while an anonymous `/api/cocoa/workspace` request is rejected by Cocoa with 401 (503 before configuration is supplied), not a generic missing-file response.
- The Google callback reaches `/api/auth/callback/google` and both approved people can sign in. An unrelated Google account and an unverified email are denied.
- Raghav creates a unique chat/note; Ananya cannot read it via UI, API parameters, owner fields, replayed paths, or a previously open Raghav tab. Repeat in the opposite direction.
- A signed-out/expired/forged session cannot read or write either workspace. Logout covers other tabs. The next person on the same browser starts with their own workspace, not a cached copy of the previous person's.
- Both Blob stores reject anonymous object retrieval. No storage token, session secret, Google client secret, email allowlist, or private data appears in static assets or public URLs.
- Neither workspace can overwrite the other's data, and two devices on the same account receive a conflict rather than silently overwriting each other.

Until Google credentials and private stores are supplied and these checks pass, this is a fail-closed implementation, **not an activated sign-in service**.
